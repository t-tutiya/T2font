# Rinkaku

T2Font（`info.someiyoshino.t2font`）の上に足すグリフ表現。TrueType の輪郭を 2 次ベジエの区間のまま持ち、画素ごとに**最近傍の区間への厳密な
符号付き距離**を求めて描く。符号付き距離の意味は T2Font の SDF と同じなので、エッジスタイル（面の縁のずらし・ぼかし・縁取りの幅・外縁のぼかし）は
SDF と同じ式のまま全値域で成り立ち、縁は表示サイズに依らず鋭い。

キーは**索引格子**: グリフを 1/indexEm em 角の格子に切り、texel ごとに「その texel の面積のどこかから見て最近傍になる区間」の集合をベイクで求めて
書く。シェーダは texel の集合（たいてい 1〜4 本）だけを評価する。符号は最近傍の区間の向き（内点は接線の右手の法線・端点は擬似法線）から決めるので、
巻き数を数える必要が無い。重なった輪郭はベイクで和の輪郭に作り直す。

本書がこのパッケージの契約の正典（データの形式・ベイクの算法・ベイク仕様・バージョン）。T2Font の契約（頂点・テクスチャ・マテリアル・シェーダ・
エッジスタイル・ベイク仕様の読み方）は T2Font の README による。

## 2. 描ける効果と支える表示サイズ

- **描ける効果**: 全部（`GlyphEffects.All`）。符号付き距離を SDF と同じ意味（インク領域の内側が正・em）で持つので、T2Font のエッジスタイルの値をそのまま使える。
- **幾何**: quad はインク境界を `GlyphEdgeStyle.MaxOuterExtentEm`（0.15em）＋最小の表示サイズの AA の半分（0.5/14 em）だけ広げた矩形
  （`RinkakuEncoding.ExtentEm`）。支える最小の表示サイズは **14px**（SDF と同じ）。
- 縁取りの外角は真の距離の等値線（円弧）で、texel による丸まりは無い。
- 効果は値域の端の組（太らせ −0.03・0.04、面のぼかし 0.06、縁取り 0.08 と外縁のぼかし 0.06、細らせと縁取り、全部の最大）で、GPU で描いた面と全体の α を、
  ページから読み戻した距離から同じ式で求めた値と画素ごとに比べて確かめる（距離が正しければ効果も正しい。式は SDF と同じ）。D3D11 の NVIDIA GeForce
  RTX 5070 Ti と AMD Radeon Graphics（統合 GPU）で、M+ 1c・M+ 2p heavy・IPAex 明朝の 18 字（広い索引の「麤」を含む）×7 組を 192px で描き、食い違う
  画素は 0、差の最大は 0.005（8bit の 1〜2 段）だった。
- **描画の時間**は画素あたり SDF の 5〜22 倍（§7）。字の多い本文には向かず、大きな字に向く。

## 3. データの形式

### 3.1 ページ

- テクスチャ 1 枚＝RGBA8・非圧縮・point・linear・ミップ無し・clamp（T2Font の `GlyphBakeContext.AddDataTexture` で作る）。**幅は常に 4096 texel**、
  高さは中身で決まり上限は `maxPageSize`（≤ 4096）。行 0 が下端。
- **線形の番地** `a = y × 4096 + x`（< 2^24 なので float で正確に持てる）。区間の表と溢れ表は線形の番地で引き、索引のブロックは 2 次元で引く。
- 1 ページの上側に索引のブロックを棚詰めし（高い順・同じ高さはグリフの順）、その下の行から区間の表を線形に並べる。上限を超えたら次のページ。

### 3.2 区間の表

グリフごとに連続した項目の列。**項目 1 つ＝texel 2 つ＝8 バイト**。区間 i は項目 i の始点・制御点と、項目 i+1 の始点（＝区間 i の終点）でできる。
輪郭ごとに区間の項目を並べ、**終端の項目**（輪郭の始点と、その擬似法線だけを持つ）で閉じる。

| バイト | 中身 |
|---|---|
| 0・1 | 始点の x（16bit・下位が先）＝`(x + 1) × 16384`。−1〜3em を 1/16384 em で持つ |
| 2・3 | 始点の y（同じ） |
| 4・5 下位 4bit | 制御点の始点からの差 dx（符号付き 12bit・2 の補数）＝`dx × 4096`。±0.5em を 1/4096 em で持つ |
| 5 上位 4bit・6 | 同じく dy（下位 4bit が 5 の上位、上位 8bit が 6） |
| 7 | 始点での**擬似法線**の角（`atan2` を 256 段・塗る側を向く）。最近傍が端点のときの符号にだけ使う |

- **塗る側は進行方向の右手**（和の輪郭・§4.1）。内点が最近傍なら、接線 `B'(t)` の右手の法線 `(B'y, −B'x)` と `p − B(t)` の内積が正なら内側。
- **擬似法線**は頂点に入る区間と出る区間の、右手の単位法線の和（2 次元では角の二等分線＝角度で重み付けた擬似法線と同じ向き）。
- **直線は制御点の差を (0, 0) にして持つ**（直線の印・出力のバージョン 3）。シェーダはこの項目を三次方程式で解かず、射影で測る（§3.5）。制御点が始点に
  重なる 2 次ベジエは始点から終点への線分そのもの（同じ点の集まり）なので、量子化で差が (0, 0) になった曲線がこの印を持っても距離は変わらない。
- **ほぼ直線の曲線は直線にする**: `|P0 − 2C + P1| < 1/1024 em`（弦からのずれ 1/4096 em 以下）。この量が小さい曲線は、閉形式の三次方程式の
  係数が小さくなって float で条件が悪くなる。
- 制御点の差が ±0.49em を超える曲線は de Casteljau で 2 分する（正確）。
- 量子化で長さ 0 になった区間は除く。

### 3.3 索引格子

- セルは `1/indexEm` em 角（既定 1/16 em）。グリフの格子は quad を覆う（左下のセル `floor(em × indexEm)`・単精度の quad をわずかに広げて覆う）。
- セルに書く**項目番号**は区間の始点の項目の番号＋1（0 は空き）。セルの集合は「セルの閉じた面積のどこかから見て最近傍になる区間」（§4.3）で、
  セルの中心に近い順（§4.3 の 4）。空きの 0 は後ろに置く（シェーダは先頭から本数だけを解く）。
- **狭い索引**（項目が 255 以下のグリフ）: セル＝texel 1 つ＝項目番号 4 つ（8bit・R G B A）。4 本を超えるセルは `(i0, i1, o, 255)` で、残りの本数と
  番号を**溢れ表**に置く。溢れ表は区間の表の直前にあり、`o` は区間の表の先頭からの**後ろ向きの texel の差**（1〜255）＝表の番地 `dataBase − o`。
  表は `[残りの本数, 番号, 番号, …]`（8bit・texel の境まで 0 で埋める）。
- **広い索引**（項目が 255 を超えるグリフ）: セル＝texel 2 つ＝項目番号 4 つ（16bit・下位が先）。4 本を超えるセルは `(i0, i1, o, 0xFFFF)`（`o` は
  16bit）で、溢れ表は `[残りの本数, 番号, …]`（16bit）。
- 1 画素の仕事は、セルの読み出しと、その本数の厳密距離（溢れ表を含めて評価本数の上限が決まる・実測は §7）。

### 3.4 セルと UV

`RinkakuGlyphCell`（グリフインデックスで引く）:

| フィールド | 意味 |
|---|---|
| `page` | ページ番号 |
| `gridX`・`gridY`・`gridWidth`・`gridHeight` | 索引格子の左下のセル（`floor(em × indexEm)`）とセルの数 |
| `blockX`・`blockY` | ページの上の索引のブロックの左下（texel） |
| `dataBase` | 区間の表の最初の項目の線形の番地 |
| `wide` | 広い索引か（セル 1 つに texel 2 つ） |
| `planeLeft`…`planeTop` | quad（em） |

画素の em 座標 `p` から索引の texel は `floor(p × indexEm) × w + K`（`w` は狭い索引 1・広い索引 2）、`K = (blockX − gridX × w, blockY − gridY)`。
`K` は x・y に `64` を足して x を 13bit・y を 11bit に詰める（`RinkakuEncoding.OffsetBias`・`OffsetXBits`・`OffsetYBits`）——頂点の UV に 24bit で
持てる。索引のブロックは `K` が収まる行（1960 行）までに置く。

**頂点**（`RinkakuRepresentation.WriteGeometry`）: quad は plane の 1 枚。**UV0.x＝`K` を詰めた値**（`RinkakuEncoding.PackedOffset`）、**UV0.y＝`dataBase`**
（広い索引は `−dataBase`・`PackedDataBase`。区間の表は索引のブロックより後ろの行なので 0 にならない）。quad の 4 頂点で同じ値で、どちらも 2^24 未満の
整数なので float で正確に持てる。シェーダは補間しない（`nointerpolation`）で受ける——補間すると丸めで 1 ずれうる。UV0.zw は T2Font の器が書く em 座標。

### 3.5 グリフ表現とシェーダ

- **グリフ表現** `RinkakuRepresentation`: セル・ページ・`indexEm` を持つ。`indexEm` をマテリアルの `_IndexEm` に載せる（`ConfigureMaterial`）ので、
  マテリアルを共有してよい範囲（`MaterialScope`）はグリフ表現自身＝フォントごと。テクスチャもフォントの境で替わるので、バッチの割れ方は SDF と同じ。
- **シェーダ** `Rinkaku/Glyph`（`#pragma target 3.5`）: texel を `Load` で整数の番地から引く（ページの高さを知らずに線形の番地を 2 次元へ直せ、UV の
  丸めの誤差も無い）。頂点と、面と縁取りの合成（S1〜S9）は T2Font の SDF のシェーダと同じで、距離の求め方だけが違う:
  1. UV0.xy から `K` と `dataBase` を取り、`floor(p × _IndexEm)` のセルの texel を読む（広い索引は 2 つ）。4 本を超えるセルは溢れ表を続けて読む。
  2. 区間ごとに項目の 3 texel（始点・制御点の差・次の項目の始点＝終点）を読む。**3 点の外接矩形までの距離（区間までの距離の下限）が今の最短より
     遠い区間は解かずに飛ばす**（セルの区間は中心に近い順に並ぶので、近い区間を先に解いて飛ばしが効く・§4.3）。**制御点の差が (0, 0) の項目（直線）は
     射影で測る**: t を 0〜1 に丸め、丸めたかで端を決めて同じ枝の中で整数に書く（帯の境で途中と端を取り違えても、そこでは接線の法線と擬似法線の符号が
     一致する）。ウェーブの中で直線と曲線が混ざれば両方の手順を進む。曲線の区間は、2 次ベジエへの最短距離を
     閉形式で解いて Newton 法で 1 回磨き、**両端の距離も必ず比べて、同じ近さ（1e−6 em の幅の中）なら端を選ぶ**。頂点が最近傍になる楔の中では、端の擬似法線でなければ符号を決められない
     （接線の法線で決めると、鋭い角の楔の中で符号を誤り、角から伸びる楔や細い線が描かれる）。閉形式の根は GPU の精度（acos・pow の近似、掛け算と
     足し算のまとめ方）で端からわずかにずれうるので、端は根に頼らずに比べる。
  3. 最も近い区間の向きで符号を決める（内点は接線の右手の法線・端点は擬似法線）。**端を選んだことは手順 2 の端を選んだ枝の中で整数に書き**、後から
     t と 0・1 を比べて決め直さない（D3D11 の GPU で、t がちょうど 1.0 なのに `t >= 1.0` の枝が通らず、終点を接線の法線で判定したことがある）。
     擬似法線（項目の 2 つ目の texel の w）は、最も近い区間が端で決まったときにだけ、ループの後で 1 回読んで復号する。
  4. 得た符号付き距離（em）で、SDF のシェーダと同じ式でエッジスタイルを塗る。
- 距離の求め方（1〜3）は `RinkakuDistance.hlsl` に置き、グリフ表現のシェーダはそれを取り込む。GPU の途中の値を読む計測のシェーダも同じ手順を取り込めるように、
  `RinkakuSignedDistance` は最も近い区間・t・両端の距離・符号を決めた法線を `RinkakuTrace` に出す（グリフ表現のシェーダは読まないのでコンパイラが消す）。
- セル 1 つの区間の数は `RinkakuEncoding.MaxItemsPerCell`（32）までで、シェーダのループの上限と同じ。超えるセルを作る字はベイクの失敗にする。
- 単精度での誤差は、シェーダの手順を写した C# のモデルと倍精度の読み戻しの差で測った（M+ 1c・IPAex 明朝・M+ 2p heavy の字で最大 1e−6 em。ほぼ全部が
  手順 2 の端を選ぶ幅で、192px で 0.0002px）。

## 4. ベイクの算法

### 4.1 和の輪郭

重なった輪郭・逆向きの輪郭・辺を共有して接する輪郭を、**非ゼロ巻き数で塗った領域の境界**へ作り直し、全部の区間を塗る側が右手に向くようにする。
重なりの内側の辺が残ると、字の中にその辺への距離の筋が出る（縁取りが字の中に描かれる）。

1. 座標が一致する端点は輪郭をまたいで 1 つの頂点にする。
2. 区間どうしの交点を求める: 制御点の境界ボックスで 2 分して絞り、弦で交わる所を求め、元の曲線の上で Newton 法で詰める。平行で同じ直線に乗る辺は、
   互いの端点のうち相手の内側にあるものを交点にする。同じ区間（向きは問わない）の重なりは分けない。
3. 交点で区間を分ける（de Casteljau・端点は共有の頂点に揃える）。
4. 分けた片の中点から左右へ 1e−7 em ずらした点の巻き数を元の全区間で数え、**片側だけが塗られる片**を残し、塗る側を右手へ向ける。同じ片の重複を除く。
5. 頂点で片を繋いで輪郭にする。頂点から進む片が複数あれば（輪郭が点で接する）、同じ元の輪郭の片を先に、次に最も右へ曲がる片を選ぶ。

**繋げない字はインポートの失敗**にし、字を名指す（黙って生の輪郭を使わない）。直すのは元フォントの側。

### 4.2 符号化

§3.2 のとおり。直線化・分割・量子化・長さ 0 の区間の除去の後で、頂点ごとの擬似法線を求める。座標が −1〜3em の外に出る字はインポートの失敗。

### 4.3 索引の構築

量子化した値を元に戻した区間（シェーダが評価する幾何と同じ）で、セルごとに:

1. セルの中心から区間への距離を取り、最小＋セルの対角の長さを超える区間を外す。距離は 1-Lipschitz なので、外した区間がセルの中で最近傍になる
   ことは無い（証明付きの上位集合）。区間の制御点の境界ボックスまでの距離は区間までの距離の下限なので、下限が明らかに大きい区間は厳密な距離を
   解かずに外す。1 本ならそれを書く。
2. 2 本以上なら、まずセルの中を通る区間を入れる（その上の点では距離 0 の最近傍なので必ず要る・セルの角をかすめるだけの区間も落とさない）。
   次にセルの閉じた面積を 7×7 の格子でサンプリングし（角と辺を含む）、隣り合うサンプルで最近傍が変わる所を 4 段まで 2 分して詰め、
   見つけた最近傍の和を書く。2 分は、その区間で 3 本目が最近傍になりうると Lipschitz で言えるときだけ下る。残る取りこぼしはサンプルの線から外れた、
   サンプルの間隔より細い領域だけで、その中の距離の誤差は Lipschitz からその幅の 2 倍以下に限られる。
3. 上位集合をそのまま書かないのは、角の外側（頂点が最近傍になる楔の領域）では隣り合う 2 区間への距離が同じ頂点への距離で等しく、上位集合が
   いつも 2 本以上になるため。どちらを評価しても距離も符号（頂点の擬似法線は両方の区間が同じ項目から読む）も同じなので、サンプリングで
   1 本（番号の小さい方）に決める。
4. セルの区間は**セルの中心に近い順**（同じ距離は番号の順）に書く。シェーダは外接矩形が今の最短より遠い区間を解かずに飛ばすので（§3.5）、
   最も近くなりやすい区間を先に解くほど飛ばしが効く。

区間への距離は、直線なら射影、曲線なら距離の二乗の導関数（三次式）の極小を、その極値（2 次方程式の根）で分けた単調な区間ごとに挟み込み付きの
Newton 法で求める。量子化した制御点が弦の上（始点と終点の間）にちょうど乗る区間は直線そのものなので直線として測る（量子化した値は 2 進の
有限小数で、この判定は倍精度で厳密）。

### 4.4 配置

§3.1 のとおり。区間の表は「溢れ表 → 項目の列」の順に並べ、`dataBase` は項目の列の先頭。

## 5. ベイク仕様（`"kind": "rinkaku"`）

| 設定 | 既定 | 意味 |
|---|---|---|
| `indexEm` | 16 | 索引格子の 1em のセルの数（8〜32 の整数）。上げると評価本数が減り、データが増える |
| `maxPageSize` | 4096 | 1 ページの最大の高さ（64〜4096 の整数・texel）。幅は常に 4096 |

```jsonc
{
    "source": "Assets/Authoring/Fonts/mplus-1c-regular.ttf",
    "coverage": "corpus",
    "charsets": ["DevelopmentDefault"],
    "representation": { "kind": "rinkaku", "indexEm": 16 }
}
```

## 6. バージョン

`RinkakuAtlasBaker.Version`（＝種類の記述子の `Version`）は**同じ入力から出る出力が変わる変更をしたら上げる**（T2Font の README §7.5）。ベイクの出力の
SHA-256（`RinkakuAtlas.ComputeContentHash`）を検査が golden と比べる。

## 7. データ量・評価本数・描画の時間・被覆の誤差

`indexEm` 16 で、JIS X 0208 を中心にした約 6,400〜8,000 字の文字セットをベイクした実測。1 字のバイト数は索引のブロック・区間の表・溢れ表の和
（ページの棚の隙間を除く）、評価本数はセル 1 つの区間の数（＝1 画素で厳密な距離を解く本数）。

| 書体 | 字数 | ページ | 漢字の平均（p95・最大） | かなの平均 | ASCII の平均 | 評価本数 平均／最大（漢字） | ベイクの時間 |
|---|---|---|---|---|---|---|---|
| M+ 1c | 6,442 | 4096×907（14.2 MB） | 2,483 B（2,964・3,608） | 1,724 B | 1,111 B | 1.89／12 | 24 秒 |
| M+ 2p heavy | 6,442 | 4096×920（14.4 MB） | 2,498 B（2,976・3,568） | 1,759 B | 1,189 B | 1.88／12 | 21 秒 |
| IPAex ゴシック | 8,014 | 4096×1160（18.1 MB） | 2,483 B（2,972・3,616） | 1,624 B | 1,100 B | 1.89／12 | 28 秒 |
| IPAex 明朝 | 8,014 | 4096×1274（19.9 MB） | 2,733 B（3,376・4,436） | 1,763 B | 1,198 B | 2.04／13 | 40 秒 |

同じ文字セットを T2Font の SDF（em48）でベイクしたときの 1 字の大きさ。SDF のセルは収めた字のインク境界の和に距離レンジを足した矩形で、全字が同じ
大きさになる（漢字も ASCII も同じ）。BC4 は 1 texel 0.5 バイトの圧縮。

| 書体 | SDF em48 のセル | R8 | BC4 | Rinkaku の漢字の平均との比（R8／BC4） |
|---|---|---|---|---|
| M+ 1c | 84×88 | 7,392 B | 3,696 B | 0.34／0.67 |
| M+ 2p heavy | 96×88 | 8,448 B | 4,224 B | 0.30／0.59 |
| IPAex ゴシック | 72×80 | 5,760 B | 2,880 B | 0.43／0.86 |
| IPAex 明朝 | 72×80 | 5,760 B | 2,880 B | 0.47／0.95 |

- 漢字の平均は 4 書体とも SDF em48 の BC4 を下回る（余裕が最も小さいのは IPAex 明朝の 5%）。M+ の 2 書体は最大の字も BC4 を下回り、
  IPAex の 2 書体は画の密な字（p95）が BC4 を上回る（SDF のセルが小さいため）。
- 評価本数の最大は全部の字で 14（IPAex 明朝の ASCII）。広い索引になる字は、この文字セットには無い（IPAex 明朝の「麤」が当たる）。
- 時間は .NET 8 の Release・論理 CPU 4 で、字ごとの処理を並列にしたもの。Unity の Editor の中では遅くなりうる。
- 各書体の乱数で選んだ 100 字（各 1,024 点）で、ページから読み戻した距離と全区間の最小の距離の差は 0。和の輪郭を作れない字は 4 書体の全字で 0。

### 描画の時間

1920×1080 の RT に字を全角送りで敷き詰めた 1 回の描画の GPU の時間（ms・D3D11・出力のバージョン 3）。SDF（em48）は字の形に依らないので本文の字だけで、
Rinkaku は M+ 1c の本文の字（ゴシック）と、IPAex 明朝のデータ量の大きい上から 40 字（明朝の密な字）で測った。括弧は SDF との比、角括弧はバージョン 2 からの変化。

| 場面 | 統合 GPU（AMD Radeon Graphics）: SDF／ゴシック／明朝の密な字 | NVIDIA GeForce RTX 5070 Ti: SDF／ゴシック／明朝の密な字 |
|---|---|---|
| 2,000 字・24px | 0.562／6.387（×11.4）［−15%］／12.458（×22.2）［−9%］ | 0.010／0.079（×7.6）［−8%］／0.150（×14.4）［−3%］ |
| 1,000 字・32px | 0.481／4.843（×10.1）［−17%］／9.676（×20.1）［−11%］ | 0.009／0.061（×6.9）［−9%］／0.118（×13.2）［−5%］ |
| 20 字・128px | 0.144／0.894（×6.2）［−25%］／1.512（×10.5）［−21%］ | 0.002／0.012（×5.0）［−14%］／0.020（×8.2）［−13%］ |
| 864 字・40px（画面を埋めた本文） | 0.633／6.141（×9.7）［−18%］／12.356（×19.5）［−13%］ | 0.012／0.078（×6.8）［−9%］／0.149（×13.0）［−6%］ |
| 600 字・48px（画面を埋めた本文） | 0.623／5.739（×9.2）［−18%］／11.332（×18.2）［−14%］ | 0.011／0.072（×6.5）［−10%］／0.137（×12.3）［−7%］ |
| 90 字・40px（30 字×3 行） | 0.066／0.635（×9.6）／1.292（×19.5） | 0.001／0.008（×7.6）／0.016（×14.5） |
| 90 字・48px（30 字×3 行） | 0.094／0.856（×9.1）／1.702（×18.2） | 0.002／0.011（×6.7）／0.021（×12.9） |
| 540 字・40px（30 字×18 行） | 0.396／3.831（×9.7）／7.717（×19.5） | 0.007／0.049（×6.8）／0.093（×12.9） |
| 450 字・48px（30 字×15 行） | 0.467／4.302（×9.2）／8.473（×18.1） | 0.008／0.054（×6.5）／0.103（×12.3） |

- 下の 4 行はメッセージウィンドウの形（1 行 30 字・行送りは字の 1.5 倍）で並べた場面で、別の回に測った（同じ出力のバージョン 3）。540 字・450 字は
  1080px の高さに入る行の数。
- **時間は字の数に比例する**。下の 4 行は、画面を埋めた場面（864 字・600 字）の時間を字の数で割り振った見積もりと、統合 GPU で ±1% の中で一致した。

- バージョン 3 で直線を射影で測るようにして（§3.5）、統合 GPU でゴシック −15〜−25%・明朝の密な字 −9〜−21% 縮んだ。大きな字ほど縮む——ウェーブが
  1 つのセルに収まり、直線だけを解く周が増える。RTX 5070 Ti の値は描画 1 回が短く 3 桁目の分解能が粗い（128px で ±数 %）。
- 画素あたり SDF の 5〜22 倍。本文のように字の多い画面には向かず、拡大で利得の出る大きな字（見出し・字の拡大演出）に向く。時間は字の数より
  画素の数で決まるので、メッセージウィンドウ（数行・100 字前後）の本文なら画面を埋めた場合の 1/8 程度になる。
- （以下 3 項はバージョン 2 で調べたこと）外接矩形で解く区間を減らしても（§3.5）縮みは 3〜17% だった。区間の texel を 4 本まとめて解く前に読み、依存する読みの回数（8×8 画素のウェーブで
  ゴシック 24px 約 6 回・明朝の密な字 約 13 回）を半分以下にする形も試したが、時間は ±2.4% の中で変わらなかった（4 本に満たないセルでも 16 texel を読む分、
  ゴシックではわずかに遅い）ので採らない。読みの待ちは同時に走るウェーブで隠れている。
- 画素あたりの時間は 24px から 128px で約半分になる。ベイクの出力から数える量（読みの回数・解くループの回数・読む区間の種類）は、画素の数で割る限り
  どれもその減り方を説明しないが、ウェーブの数（画素数 ÷ ウェーブの埋まり。quad の縁のウェーブは空きのレーンを持ち、24px で 8 割・128px で 96%）で
  割り直すと、ゴシックは解くループの回数（8×8 のウェーブの画素の和集合）1 項で 5 場面が ±4% に収まる。明朝の密な字は 128px が 15% ほど軽く残る
  （ウェーブが読む区間の種類の差の範囲）。時間を決めるのは解くループの回数で、読みは待ち（依存の深さ）ではなく、効くとしても 1 命令で引く番地の種類。
  演算と読みの種類のどちらが律速かは、働きを外した変種のシェーダで同じ場面を測って切り分けた（下表）。
- **働きの取り分**（変種のシェーダ: 全部＝手順そのまま／読むが解かない＝読みとループは同じで三次方程式の代わりに読んだ 3 点への距離／読まずに全部を解く＝
  区間の texel を読まず番号と画素から作った区間を全部解く／読んで全部を解く＝外接矩形で飛ばさない／セルだけ＝セルと溢れ表の先頭だけ読む。「全部」は
  `Rinkaku/Glyph` と 3 桁まで同じ）。解く＝全部 − 読むが解かない（三次方程式と直線の射影）、区間の読み＝読んで全部 − 読まずに全部、床＝セルだけ、残り＝
  ループの制御・セルの復号・外接矩形の検査・擬似法線の後読み。括弧は「全部」に対する割合。出力のバージョン 3。読まずに解く変種は直線か曲線かを読めない
  ので、番号から擬似乱数で約 3/4 を直線として解く（区間の読みの取り分は近似）。

| 場面・書体 | 統合 GPU: 全部／解く／区間の読み／床／飛ばしの利得 | RTX 5070 Ti: 同じ並び |
|---|---|---|
| 2,000 字・24px・ゴシック | 6.391／2.16（34%）／1.28（20%）／0.81（13%）／−0.21（−3%） | 0.080／0.025（31%）／0.022（28%）／0.014（18%）／0.001（1%） |
| 2,000 字・24px・明朝の密な字 | 12.465／4.69（38%）／3.27（26%）／1.00（8%）／0.87（7%） | 0.150／0.052（35%）／0.048（32%）／0.017（11%）／0.013（9%） |
| 864 字・40px・ゴシック | 6.146／1.89（31%）／1.33（22%）／0.91（15%）／−0.37（−6%） | 0.078／0.023（29%）／0.022（28%）／0.016（20%）／0.000（0%） |
| 864 字・40px・明朝の密な字 | 12.361／4.37（35%）／3.15（26%）／1.12（9%）／0.36（3%） | 0.149／0.049（33%）／0.046（31%）／0.018（12%）／0.007（5%） |
| 20 字・128px・ゴシック | 0.895／0.17（19%）／0.21（23%）／0.21（23%）／−0.11（−12%） | 0.012／0.003（20%）／0.004（32%）／0.003（28%）／0.000（−3%） |
| 20 字・128px・明朝の密な字 | 1.512／0.35（23%）／0.49（32%）／0.23（15%）／−0.09（−6%） | 0.020／0.005（23%）／0.008（37%）／0.004（19%）／0.000（0%） |

- 律速は 1 つではない。バージョン 2 では三次方程式が 32〜44% だった。直線を射影で測るようにして、解く取り分は統合 GPU でゴシック 19〜34%・明朝 23〜38% に
  下がり、区間の読み 20〜37%・床 8〜28% が相対的に大きくなった。区間の読みは、先読みで依存の深さを半分以下にしても変わらなかった分なので（バージョン 2）、
  待ちではなくテクスチャの処理量（命令の数と引く番地の種類）。
- **外接矩形の飛ばしの利得は、ゴシックで負になった**（統合 GPU で −3〜−12%）。明朝の密な字は曲線が多く、小さな字ではまだ正（+3〜+7%）。
  直線だけ検査を省く形も試したが、ゴシックは −2〜+1%・明朝の密な字は最大 +4% 遅くなったので採らない（検査で飛ばしていた直線の分だけ解く数が増え、
  ゴシックで重いのは検査の分岐とループの制御の方と見る）。検査を全部やめるとゴシックは速くなるが明朝は遅くなる（書体で逆になる）。
- 読みの取り分には、読まずに解く変種が区間の形を作り物にする分（直線と曲線の割合・三次方程式の枝の割れ方が本物と違う）が混じる。取り分の境は
  ±数 % の幅で見る。
- 残る手立ては、項目を 1 texel に詰める形式・効果の外延の宣言（quad の画素を減らす）。

### 被覆の誤差

同じ字を同じ大きさで、Rinkaku（シェーダの手順の単精度のモデル）と T2Font の SDF（em48・R8・開発用の文字セットのセルの箱・bilinear）で描き、理想の被覆
（元の輪郭を画素あたり 16×16 で塗った面積）と画素ごとに比べた。字は M+ 1c のあ・永・鬱・■、IPAex 明朝の永・鬱、M+ 2p heavy の喙の 7 字。外縁は縁取り
0.08em の全体の α。数字は 7 字の平均（MAE）と和（誤差 0.25 超の画素）で、Rinkaku／SDF。

| px | 面 MAE | 面の誤差 0.25 超の画素 | 外縁 MAE | 外縁の誤差 0.25 超の画素 |
|---|---|---|---|---|
| 40 | 0.0049／0.0087 | 8／22 | 0.0022／0.0031 | 7／2 |
| 48 | 0.0039／0.0108 | 14／169 | 0.0018／0.0035 | 5／14 |
| 64 | 0.0028／0.0094 | 12／308 | 0.0014／0.0033 | 13／34 |
| 128 | 0.0012／0.0092 | 8／1544 | 0.0006／0.0035 | 7／324 |
| 192 | 0.0008／0.0090 | 3／3497 | 0.0004／0.0035 | 13／1229 |

- SDF の誤差の大きい画素は大きさとともに増える（角の丸まり＝em48 の texel が表示で数画素になる）。Rinkaku は大きさに依らず数画素で、距離のランプと
  面積が角で食い違う分（距離を SDF と同じ意味で持つ限り残る）。
- 40px の外縁だけは Rinkaku の誤差 0.25 超が多い。縁取りの外角は真の距離の円弧（半径 0.08em）で、細い円弧ではランプが面積から離れる。

## 8. 既知の制限

- **点で接する輪郭の頂点**: 2 つの領域が 1 点で接する頂点では、擬似法線が片方の領域の角だけで決まる。その頂点が最近傍になる点のごく一部で符号を
  誤りうる（字の外の 1 点のまわり）。
- **細い取りこぼし**: §4.3 の 2 のとおり、セルを通らない区間が、サンプルの線から外れたサンプルの間隔より細い領域でだけ最近傍になると落としうる
  （距離の誤差はサンプルの間隔の 2 倍以下＝`indexEm` 16 で 1/48 em 以下）。§7 の検証では見つかっていない。
- **擬似法線の量子化**: 1.4° の段なので、内角が約 1.4° より鋭い角の先端では、端点が最近傍の点の符号を誤りうる。
- **ほぼ直線の曲線**: 弦からのずれが 1/4096 em 以下の曲線は直線として描く。
