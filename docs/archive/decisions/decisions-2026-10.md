## 2026-10-29 用語をカタカナの一般的な訳語へ揃える — D-TERMS

**発端**: パッケージのコメント・README・文書が「焼く・焼き器・取込器・墨の外接・字形・字の表・様式（縁）・距離域・超標本化」など、
一般的でない訳語や造語を使っていた。Unity（アセット・インポーター）やフォント技術（グリフ・ベイク）で通じる語と対応が取りにくく、
パッケージを使う側にも読みにくい。

**決定**: 一般的でない訳語を避け、カタカナ英語か「カタカナ英語＋する」を使う。訳語の表は `docs/reference/terminology.md` を正典とし、
プロジェクト全体（パッケージのコメント・例外とログの文面・README、`Assets/` と `Tests/` のコードとテストの名前、生きた文書）に適用する。
導入時に既存の記述を一括で書き換えた。

**採らなかった案**: 英語の識別子の改名（訳語は日本語の地の文だけの問題で、API を変える理由にならない）。歴史記録・公開済みの CHANGELOG・
テンプレートが管理するファイルの書き換え（歴史は当時の語で読むもの・テンプレート由来の文書はテンプレート側で直す）。

**守ること**: 新しい用語は表に足してから使う。文字データ（ベイクする字・描画の見本）は訳語の対象ではないので変えない。

## 2026-10-28 ドキュメントの重複排除と軸別正典 — D-DOCDUP

**決定**: 正典は「どの文書が偉いか」ではなく「**その記述は何を語っているか**（軸）」で決める。なぜそうしたか＝`archive/decisions/`／
どうなっているか＝`architecture/`／どう書くか＝`reference/`（機械生成分は `generated/`）／いつ何が終わったか＝完了記録／
次に何をやるか＝`roadmap.md`／これから作る物の設計＝`plans/`。正典以外は**決定 ID か章名で参照し、要約し直さない**。
軸が重なって 2 文書のどちらにも書けるときは「梯子」（`docs/README.md`「ドキュメント運用ルール」）で上に居るほうが持つ。

**理由**: 重複は逐語ではなく言い換えで起き、単位は「1 つの裁定」である。同じ決定が複数の文書で別の言葉で書き直されると、
grep では見つからず、どれが正典かも分からず、読み手は全部読むまで「これで全部か」が判らない。そして更新は片方にしか届かない
——**重複は情報を増やさず、陳腐化する面を増やす**。

## 2026-10-28 ドキュメントを軸ごとのフォルダへ分ける — D-DOCTREE

**決定 1**: `docs/` を記述の軸ごとのフォルダに分ける——`reference/`（どう書くか）・`generated/`（自動生成・手で直さない）・
`architecture/`（どうなっているか）・`guides/`（どう作業するか）・`plans/`（これから作る物）・`archive/`（なぜ・いつ終わったか・凍結文書）。
`docs/` 直下は索引と roadmap だけにする。

**決定 2**: ファイル名は移設しても変えない。コード・データ・文書はファイル名と § 番号で参照するので、名前を保てばフォルダを
動かしても意味は壊れない。

**決定 3**: 文書を指す参照は機械が見る（`Tests/DocsReferenceIntegrityTests.cs`）。移設・退避では参照を同じコミットで直す。
**歴史記録（decisions・完了記録・評価・凍結文書）はリンクだけを張り直し、地の文の当時のパスは書き換えない**——地の文は
「いつどこにあったか」という事実だから。削除・改名した文書を名指したいときは、パスではなく決定 ID を書く。

**理由**: 軸の表が正しくても物理配置に表れていないと、書き手は読む先が複数あるように見え、境界から両向きに記述が漏れて
食い違いが生まれる。移設で壊れる参照は人の注意では追えない。

## 2026-10-28 設計文書のライフサイクルを二択にする — D-DOCLIFE

**決定 1**: 実装が完了した `plans/` の設計文書は、①`archive/completed-designs/` へ凍結退避する（削除しない・冒頭に凍結バナー）か、
②`plans/` に残して**冒頭バナーに「本書が現役なのは〜を所有するため」を明記する**、のどちらかを必ず満たす。所有物は
他のどの正典にも移せていないもの（申し送り・未着手の設計・後続が読む手順）に限る。移せるものが残っていなければ ① を選ぶ。

**決定 2**: 現役理由の正典は文書冒頭のバナーで、索引（`plans/README.md`）には複製しない。索引は対象の 1 行説明に留める。

**決定 3**: 索引の整合は機械が見る。設計判断ログは `Tests/DecisionsIndexIntegrityTests.cs`（①月見出しの「（N 件）」＝索引行数
②本文に現れる全日付が索引にも行を持つ）、完了記録とフォルダの索引は `Tests/DocsIndexCoverageTests.cs`。

**理由**: 処方が決まっていても、規約を機械が見ていなければ静かに破れる。二択にしないと「現役理由」が退避を回避する呪文になる。
「見出し数＝索引行数」を課さないのは、追記が独自の索引行を持つ／2 見出しが 1 つの決定を成す、の 2 形が正当に存在するからで、
日付の包含関係なら除外リストなしで成立し、実際に起きる失敗（今日の決定を本文にだけ書く）を捕まえる。

## 2026-10-28 完了記録を月別ファイルへ分割する — D-CRMONTH

**決定**: 完了記録は設計判断ログと同じ形にする——索引 `archive/completed-roadmap.md` ＋ 本文 `archive/completed-roadmap/completed-roadmap-YYYY-MM.md`。
新しい項目は当月ファイルの先頭へ追記し、索引にも 1 行（`完了日 ｜ 完了項目 ｜ 決定 ID`）足して月見出しの件数を合わせる。
完了日は roadmap に書かれていた表記のまま載せ（幅のある表記もそのまま）、どの月へ入るかは最後の日付で決める。

**理由**: 月は全順序なので、目標やマイルストーンの区切りは必ず月の境界に含まれる。同じものを 2 つの軸で分けると、
どちらのファイルを見ればよいかが項目ごとに変わる。索引と本文が別ファイルになって初めて、両者の対応を機械検査できる。

## 2026-10-28 リモートの検証経路を push → CI にする — D-ENV4

**決定 1**: リモートセッションのネットワークポリシーを、コンテナへ .NET SDK を入れるためには開けない。開けて得られるのは
CI（`quality.yml`）の部分集合（NUnit だけ）で、CI は NUnit・空白整形・editorconfig・Unity コンパイルまで見る。

**決定 2**: 「コンテナ内で直接回せるか」と「検証できるか」を区別する。ブランチを push して `quality.yml` を手動実行（`workflow_dispatch`）
すれば、どの環境からも検証できる（検証経路③）。ローカル PC へ委譲が要るのは **Play Mode テストと実機目視だけ**になる。

**決定 3**: リモートでは検証とコミットの順序が逆になる（コミット → push → CI 確認 →〔赤なら修正コミット〕）。ステップ単位で
進める原則は変わらず、確認の位置だけが後ろへずれる。

**理由**: 使える手段があるのに、環境判定が「実行可能な検証: なし」としか言わないと、使わない判断が繰り返される。

## 2026-10-28 サブエージェントと CI の監視の運用 — D-AGENTOPS

**決定 1**: サブエージェントは原則使わない（ユーザーが明示したときだけ）。調査は主セッションで、見出しから位置を取って絞って読む。

## 2026-10-28 生成物の再生成をリモートから回す経路 — D-REGEN

**決定 1**: 生成物の書き出しは、検査ゲート（`quality.yml`）とは別のワークフロー `regenerate.yml` が持つ。起動は `claude/**` への push で、
最後のコミットのメッセージに `[regen]` を含むときだけ。`UPDATE_GENERATED=1 dotnet test` の差分を bot が同じブランチへコミットして push する。

**決定 2**: 生成物の検査と書き出しは `Tests/GeneratedGolden.cs` の 1 つの手順に揃える（通常のテスト実行はリポジトリを 1 バイトも書かない）。

**理由**: リモートのコンテナには dotnet が無く、生成元を変えると CI が赤のまま止まる。ログからパッチを書き写すと誤写が golden テストに
弾かれるまで分からないが、bot のコミットなら中身はバイト単位で生成器の出力のままになる。帰結: `GITHUB_TOKEN` による push は他の
ワークフローを起動しないので、再生成の後は `quality.yml` を手動実行し、ブランチを pull してから次のコミットを積む。

## 2026-10-28 生成物の改行を LF に固定する — D-GENEOL

**決定**: 改行 LF は**ファイルの性質ではなく生成器の契約**とする。C# の生成器は `GeneratedText.AppendLineLf`（`AppendLine` を使わない）と
`GeneratedText.NormalizeNewlines` を使い、Python は `newline=""` を渡す。対象はコミットされる生成物だけで、コンソール出力・診断・
セーブデータは OS 既定の改行のままでよい。

**理由**: `AppendLine` や整形器は OS の改行を使うので、同じ入力から Windows では CRLF が出る。`.gitattributes` が改行を畳むため
`git diff` は空なのに `git status` だけが M を出し、作業ツリーが恒常的に汚れて本物の差分が埋もれる。CI は常に LF のクリーンな
チェックアウトなので、ファイル側の検査では原理的に捕まえられない——だから生成器の側で守る。

## 2026-10-28 Core の nullable を 2 つのコンパイル世界で揃える — D-NRTCORE

**決定**: Core（Unity 非依存の asmdef）は Unity と外部 NUnit（`dotnet test`）の両方からコンパイルされるので、nullable の文脈と強度を
両側で揃える。Core の全 `.cs` は先頭に `#nullable enable` を持ち（`Tests/CoreNullableCoverageTests.cs` が固定）、asmdef の隣の
`csc.rsp` で nullable 警告をエラー化する（外部 csproj の `<WarningsAsErrors>Nullable</WarningsAsErrors>` と同じ強度）。

**理由**: 片側だけで設定すると「Unity では無警告で書けて、`dotnet test` で初めて落ちる」食い違いが生まれ、開発者が常には回せない
側でしか顕在化しない。`csc.rsp` にはコメント行を書かない（Unity のコンパイルが失敗する。理由は `docs/guides/code-quality.md`）。

## 2026-10-28 テストスイートの三層化と Fake の単一正典 — D-TESTARCH

**決定 1（三層）**: テストは外部 NUnit（`Tests/`・UnityEngine 型ゼロの Core）／EditMode（Unity 型を使う同期ロジック）／
Play Mode（フレームループが要るもの）の三層に置き、**安い層で表現できるものは安い層へ置く**。判定基準は `docs/guides/testing-workflow.md`。

**決定 2（Play Mode 内の分離）**: 実データを読む統合テストは `Assets/Tests/PlayMode/Integration/` だけに置き、要素ごとのフォルダ
（`Assets/Tests/PlayMode/<要素>/`）は Fake だけを使う。

**決定 3（規約 R1〜R3）**: R1 テストダブルは Core のアルゴリズムを再実装しない／R2 共有 Fake は各 1 個（Core にだけ依存するものは
`Assets/Tests/CoreSupport/`、Unity 側だけのものは `Assets/Tests/Shared/`）／R3 実データは統合テストだけが正典のローダ経由で読む。

**理由**: 層の責務が分かれていないと、速く回せるはずのテストが遅い層に溜まり、同じ目的の Fake が複製されて食い違う。

## 2026-10-28 省略可能引数を本番 API に置かない — D-ARGOPT

**決定 1**: 本番 API に省略可能引数（とくに `= null` の既定値）を新設しない。既定値が要るのがテストだけなら、既定値は共有テスト支援
（`Assets/Tests/CoreSupport/`）の組み立て関数が持つ。

**決定 2**: `null` の意味で処方を分ける。空のコレクション → 非 null の空の値。別モード → Null Object を用意して引数を必須にする。
真の任意（`innerException` 等）だけが省略可能のまま残る。診断の受け口（`Action<string>? warn = null` 等）は必須にし、捨てる場所を明示する。

**理由**: 既存メソッドへ末尾の `= null` を足すのは、入れた瞬間には何も壊れない最小コストの手で、レビューでしか止まらない。その実態は
「本番は常に全部渡し、既定値を使うのはテストだけ」——テストの都合が本番 API の形を決めている。省略した側で警告が黙って消えると、
「本番だけ警告が出る」非対称も生まれる。

## 2026-10-28 Unity の版は LTS の最新パッチに合わせる — D-UNITYVER

**決定 1**: Unity は LTS 系列の中で最新パッチへ上げる。上げる前に `ProjectVersion.txt` だけを変えたブランチで CI を回し、GameCI の
イメージがあることとコンパイル結果が変わらないことを確かめる。版上げそのものは Unity Editor で行う（Editor が `ProjectVersion.txt`・
`packages-lock.json`・`ProjectSettings` を書き直すため）。

**決定 2**: LTS でないマイナー版へは出荷まで上げない。見直すのは、出荷の後／出荷が LTS のサポート終了を越えそうなとき／LTS に来ない
修正が必要になったとき。

**決定 3**: 開発に使う全 PC と CI を同じ版に揃える。CI とローカルの `Tools/verify-unity-compile.ps1` は `ProjectVersion.txt` から版を読むので、
ファイルの更新だけで揃う。

**理由**: パッチの遅れは溜めるほど一度に変わる量が増える。一方、マイナー版の更新には既存プロジェクトの挙動やアセットの書式を変えるものが
あり、制作の途中で踏む理由が無い。
