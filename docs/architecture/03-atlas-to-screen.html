1全体の流れ

パッケージは字を画面へ置く側（ホスト）と、インクの描き方（表現）を分ける（README §4.1）。ホストは表現の具体型を知らず、グリフインデックスを渡して幾何とテクスチャを受け取り、マテリアルを GlyphMaterialCache から引いて、uGUI の CanvasRenderer へ渡すだけ。本書のホストは検証ビュー T2FontText で、文字列 1 本を字ごとに 1 つの CanvasRenderer で描く（README §10）。利用側のテキスト描画も、①〜④を自分のコードで行えば同じ流れになる。

2アセットを読み込む

ロードの単位は T2FontAsset（ScriptableObject）。インポーターがメインアセットとして登録し、表現 SdfRepresentation とページの Texture2D をそのサブアセットにしてある（02 章 §7）。ほかのアセットを指すのは表現のシェーダの参照だけなので、T2FontAsset を参照すれば（シリアライズしたフィールド・AssetDatabase.LoadAssetAtPath・利用側のロードの仕組み）、描くのに要る物が一度にそろう。検証ビューはフィールド font で参照する。

ページは Read/Write を無効にしてあるので（02 章 §7）、Unity は GPU へ上げた後に CPU 側の写しを持たない。読み込みの時点では計算は何もしない。マテリアルはまだ無く、ホストが GlyphMaterialCache で作る（§5）。作る時点はフォントを読んだ時点がよい（Prewarm・README §4.5）——描画中に作るとヒッチになる。検証ビューは最初の Rebuild で作る。

T2FontAsset には実行時の状態が 1 つだけある。無い字を報告済みかの記録で、直列化せず、再生の開始ごと（RuntimeInitializeLoadType.SubsystemRegistration）に捨てる（§3.1）。

3字を並べる

T2FontText.Rebuild は、文字列を頭から 1 字ずつ読み、グリフインデックスを引き、ペンを進めながら字ごとに §4〜§6 を回す。行送りは改行（U+000A）だけで、折り返し・カーニング・縦書きは持たない（README §10）。

3.1字からグリフインデックスへ

TextCodepoints.Read は文字列を UTF-16 の符号単位ではなく字（コードポイント）で読む。サロゲートペアは 1 字になり、片割れのサロゲートはその値のまま 1 字として返す——フォントに無い字として代替グリフで見え、誤りが黙って消えない（README §2.1）。

T2FontAsset.Resolve は昇順の codepoints を二分探索し、見つかった添字をそのままグリフインデックスにする（README §3.2）。間接の表は無く、割り当ても無い。無い字は notdef を返し、コードポイントごとに 1 回 LogError を出す。見本の文字列では全部の字が見つかる。

3.2ペンを進める

ペン原点は RectTransform の矩形の左上から 1 行目のアセンダぶん下、(rect.xMin, rect.yMax − ascender × fontSize) から始まる。字ごとに Metrics(glyph).advance × fontSize だけ右へ進め、改行では x を rect.xMin へ戻して y を (ascender − descender + lineGap) × fontSize だけ下げる。値はすべて em なので、表示サイズは最後に掛けるだけ（README §3.3）。

4幾何を書く

4.1GlyphGeometry

GlyphGeometry は表現がグリフの幾何を書き込む器で、ホストが 1 つを持ち回し、字ごとに Clear して使う（割り当て無し）。表現が呼ぶのは 2 つだけ。

  • AddVertex(emX, emY, u, v): 位置 (emX, emY, 0) と UV0 (u, v, emX, emY) を足す。UV0.zw は器が位置から書くので、表現は zw を書けない。シェーダはその微分から 1 表示 px が何 em かを得る（README §4.2・§5 S3）。
  • AddTriangle(a, b, c): 頂点の番号で三角形を足す。AddQuad は頂点 4 つ（左下・右下・右上・左上）と三角形 2 つ (0, 2, 1)・(0, 3, 2) を書く便宜のメソッド。

幾何は quad に限らない（README §4.2）。インクの無いグリフでは表現は何も書かず、ホストは VertexCount が 0 ならその字を描かない。

4.2SDF の quad と UV

SdfRepresentation.WriteGeometry は、グリフインデックスでセル SdfGlyphCell を引き、AddQuad を 1 回呼ぶ。位置はセルの plane（em）、UV はセルの atlas（ページの px）をページの寸法で割った値。plane と atlas は同じ矩形を 2 つの座標系で書いたもので、atlas ＝ 原点 ＋ plane × emPx が厳密に成り立つ（02 章 §6.2）。だから quad の中で em と UV は同じ一次式で動き、bilinear で読む位置がずれない。

4.3Mesh へ詰める

GlyphGeometry.CopyTo(mesh, fontSize) は、位置だけに表示サイズを掛けて Mesh へ詰める（SetVertices → SetUVs(0, …) → SetTriangles。頂点の数が決まる SetVertices が先）。UV0 は掛けないので、zw は em のまま残る——位置は表示 px、zw は em になり、その比が 1 表示 px あたりの em になる（§8.4）。uGUI のバッチは UV0 の 4 成分を保つ。

検証ビューは字ごとに Mesh を 1 つ作る（HideFlags.DontSave）。Mesh はネイティブのオブジェクトで GC では回収されないので、作り直すときと破棄のときに明示的に捨てる。

5マテリアルとテクスチャを用意する

GlyphMaterialCache は、（表現の MaterialScope・エッジスタイル）を鍵にマテリアルを 1 つずつ作って持つ（README §4.5）。Get は次の順に動く。

  1. 鍵で引き、あればそれを返す。
  2. Check: エッジスタイルの値が範囲の内か（FindOutOfRange）、使う効果（値が 0 でないキー）を表現が描けるか（style.Uses & ~representation.Effects）。合わなければ例外で止める——黙って近似すると表現によって見た目が変わる（README §6.3）。検証ビューは Rebuild の頭で同じ検査をし、合わなければ LogError を出して何も描かない。
  3. new Material(representation.Shader)（HideFlags.DontSave）。
  4. representation.ConfigureMaterial(material): 表現の定数。SDF は _RangeEm に SdfEncoding.RangeEm（0.1875）を入れる。
  5. WriteEdgeStyle: エッジスタイルの 5 値を uniform へ 1 対 1 で入れる。縁取りの色は sRGB で持ち、色空間が Linear のプロジェクトでは linear に直して SetVector で入れる（Vector は Unity が色空間の変換をしないので）。α は直さない。

SDF の MaterialScope はシェーダ（既定のまま）で、距離レンジは全フォント共通なので、全 SDF フォントがエッジスタイルごとに 1 つのマテリアルを共有する。面の色とフェードは頂点色で（README §5 S2）、ページは _MainTex として字ごとに渡すので、どちらもマテリアルを分けない。見本の文字列は 1 つのマテリアルで描ける。

テクスチャは SdfRepresentation.GetTexture(glyph) が pages[cell.page] を返す。インクの無いグリフでは呼ばれない。マテリアルはネイティブのオブジェクトなので、所有者は Dispose（全部）か Release(scope)（そのフォントの分）で捨てる。検証ビューは OnDisable で Dispose する。

6CanvasRenderer へ渡す

検証ビューの CreateGlyph は、インクのある字ごとに、子の GameObject（RectTransform と CanvasRenderer・HideFlags.DontSave）を作り、pivot を 0、sizeDelta を 0、localPosition をペン原点にする。そのうえで CanvasRenderer の口へ次の順に渡す。

  • 色: SetColor(faceColor.rgb, alpha)。Canvas が頂点色として渡し（色空間の扱いは §9.2）、シェーダは rgb を面の色、α をフェードとして最後に 1 回だけ掛ける（README §5 S2）。CanvasRenderer の色はバッチの鍵に入らないので、色違いの字もまとまる。
  • クリップ: ClipToRect のとき、自分の矩形を最上位の Canvas の空間へ写して EnableRectClipping(rect) に渡す（RectMask2D と同じ取り方）。

見本の文字列では、空白を除く 9 字ぶん、GameObject・CanvasRenderer・Mesh が 9 組できる。ここまでが C# の仕事で、値が変わらない限り次のフレームからは何もしない（§10）。

7Canvas がバッチにまとめる

CanvasRenderer は自分では描かない。親の Canvas が、配下の CanvasRenderer の幾何を集め、描く順に並べ、同じマテリアル × 同じテクスチャが続く所を 1 回の描画（バッチ）にまとめる（README §4.4）。このとき頂点はルートの Canvas の空間へ写され、CanvasRenderer の色が頂点色に入る。矩形クリップを有効にした字のバッチには、Canvas がキーワード UNITY_UI_CLIP_RECT と _ClipRect を渡す。

Canvas は変わった所だけバッチを作り直し、変わらなければ前のフレームのバッチをそのまま描く。GPU は毎フレーム描くが、C# の側（§3〜§6）は値が変わったときしか回らない。

8GPU で描く

バッチ 1 つが描画の呼び出し 1 回になり、GPU の上で下の段を流れる。シェーダは README §5 の契約（S1〜S8）を満たす。

8.2頂点シェーダ

入力は POSITION・COLOR・TEXCOORD0（float4）だけ（README §5 S1）。追加の頂点チャネル（Canvas.additionalShaderChannels）は Canvas 全体の設定なので使わない。vert は位置を UnityObjectToClipPos でクリップ空間へ写し、色と UV0 はそのまま渡し、クリップの判定用に位置（ルートの Canvas の空間）を canvasPos として渡す。_ClipRect も同じ空間で来るので、そのまま比べられる。

8.3ラスタライズ

GPU は三角形が覆う画素の中心ごとにフラグメントを 1 つ作り、頂点の値（色・UV0・canvasPos）を三角形の中で補間して渡す。quad の 2 つの三角形は対角線を共有するので、境の画素は片方にだけ入る。フラグメントは 2×2 の画素を組にして回すので、ddx・ddy は隣の画素との値の差として取れる。

見本では fontSize が emPx と同じ 48 なので、「あ」の quad は画面でもページと同じ 57×60 px になり、1 画素がおよそ 1 texel に当たる（ペン原点が画素の格子に揃っていないぶん、読む位置は texel の中心からずれる）。fontSize を変えると、同じ quad が画面の多い（少ない）画素を覆い、ページを bilinear で拡大（縮小）して読む。

8.4フラグメントシェーダ

frag は画素ごとに次を計算する。図 8 は各段の値を、同じ式で CPU で計算した画像。

  1. 距離を読む: s = (tex2D(_MainTex, uv0.xy).r − 0.5) × 2 × _RangeEm。符号化（02 章 §6.1）の逆で、輪郭からの距離（em・インク領域の内側が正）に戻す。距離は bilinear で補間して読むので、ページの texel より細かく輪郭が決まる。
  2. 1 表示 px の em: emPerPx = ½ (|∇uv0.z| ＋ |∇uv0.w|)（∇ は ddx・ddy の組）。UV0.zw は quad の中で一次なので微分は quad の中で一定で、回転・拡縮しても正しい（README §5 S3）。回転も拡縮もしない見本では 1 ÷ 48 ≒ 0.02083em。距離 s の fwidth を使わないのは、bilinear の区分ごとに値が変わり、距離レンジの外では 0 になるため。
  3. 2 つの境界: 面の縁は s = −_FaceDilate、縁取りの外縁は s = −(_FaceDilate ＋ _OutlineWidth)。
  4. 被覆率: 縁取り込みの形 ao = saturate((s − 外縁) ÷ (emPerPx ＋ _OutlineSoftness) ＋ 0.5)、面 af = min(saturate((s − 面の縁) ÷ (emPerPx ＋ _FaceSoftness) ＋ 0.5), ao)。ランプは境界を中心に置くので、ぼかしを足しても 50% の位置は動かない（README §6.1）。ぼかしが 0 ならランプの幅は画面の 1px。
  5. 入れ子の面積で合成する: 面が af、縁取りの帯が ao − af。aOutline = _OutlineColor.a × (ao − af)、a = af ＋ aOutline、premultiplied の色 face.rgb × af ＋ _OutlineColor.rgb × aOutline を足してから a で割って straight に戻す（README §5 S4）。
  6. フェード: 出力の α に頂点色の α を最後に 1 回だけ掛ける（README §5 S2）。

8.5クリップ

キーワード UNITY_UI_CLIP_RECT が有効なバッチでは、出力の α に UnityGet2DClipping(canvasPos.xy, _ClipRect) を掛ける。矩形の内なら 1、外なら 0 で、矩形の外の画素は α 0 で書かれる（描かれない）。

8.6ブレンドしてレンダーターゲットへ書く

フラグメントの出力は、レンダーターゲットの今の画素（dst）と次の式でブレンドして書かれる。

rgb ＝ src.rgb × src.a ＋ dst.rgb × (1 − src.a)　　a ＝ src.a × 1 ＋ dst.a × (1 − src.a)

rgb は straight α の合成、α は over 合成。不透明な背景（バックバッファ）の上では普通の重ね塗りになる。透明にクリアした RenderTexture の上では、rgb は premultiplied（色 × α）になり、α は 1 回だけ掛かる。α も SrcAlpha で合成すると α が二乗され、その RenderTexture を重ねたときに下層が漏れる（README §5 S6）。

背景は比較の場面のカメラの背景色 (0.32, 0.36, 0.42)（sRGB）を linear に直した (0.0835, 0.1065, 0.1473)（α 1）、透明の RT は (0, 0, 0, 0) にクリアした RenderTexture。8bit の値は sRGB のレンダーターゲットへ書いたときに残る値（§9.2）。最後の行で α も SrcAlpha で合成すると、α は 0.686² ≒ 0.471 になる。

9レンダーターゲットから画面へ

9.1Canvas の描画モード

どのレンダーターゲットへ、いつ描くかは Canvas の描画モードで決まる。シェーダとマテリアルはどのモードでも同じ。

描画モード描く者と時点レンダーターゲットunity_GUIZTestMode
Screen Space - OverlayURP が UI のパスで、シーンを描いた画像の上へ（カメラを持たない）画面（バックバッファ）Always
Screen Space - Camera指定のカメラが、透明物の並びの中でカメラのカラーターゲットLessEqual
World Spaceシーンを描く各カメラが、透明物の並びの中で（3D の配置に従って前後する）カメラのカラーターゲットLessEqual

URP では Overlay の Canvas も URP が描く。SupportedRenderingFeatures.rendersUIOverlay は UI のオーバーレイを描く処理をエンジンではなく SRP が呼ぶことを表し、URP のカメラの描画（Render Graph）には UI を描くパスがある。unity_GUIZTestMode は Canvas が描く直前に入れる値で、Overlay では Always、ほかでは LessEqual になる。

カメラのカラーターゲットは、URP が中間のカラーテクスチャを使うときはそのテクスチャで、最後にバックバッファへ写す（ブリット）。使うかどうかは、Universal Renderer の Intermediate Texture が Auto（既定）なら URP が描画の内容から決める。どのレンダーターゲットへどの順に描かれたかは、Render Graph Viewer（Window > Analysis > Render Graph Viewer）か Frame Debugger で確かめられる。

Overlay では、ルートの Canvas の空間は画面の px に CanvasScaler の倍率を掛けた単位になる。どのモードでも、AA の幅は UV0.zw の微分から決めるので、倍率・カメラの距離・回転によらず画面の 1px になる（§8.4）。

9.2色空間

本プロジェクトの色空間は Linear。シェーダは linear の値で計算し、sRGB のレンダーターゲットへ書くときに GPU が linear から sRGB へ直す。ブレンドで dst を読むときは sRGB から linear へ戻すので、ブレンドも linear で行われる。§8.6 の表の 8bit の値はこの変換の後の値。

色の入口は 2 つで、扱いが違う。

  • 面の色（頂点色）: Linear のプロジェクトでは、Canvas がメッシュを作るときに gamma から linear へ直してからシェーダへ渡す（uGUI の既定）。Canvas の Vertex Color Always in Gamma Color Space（Canvas.vertexColorAlwaysGammaSpace）を有効にすると、この変換をシェーダに任せる。組み込みの UI シェーダは変換を持つが、T2Font/SDF は持たず、既定（無効）を前提にしている——有効にした Canvas では gamma の値を linear として扱うので、面の色が明るくずれる。
  • 縁取りの色: マテリアルの Vector で、Unity が変換しないので、GlyphMaterialCache が Linear のときに linear へ直して入れる（§5）。

9.3画面へ出す

フレームの描画が終わると、Unity はバックバッファ（スワップチェーンの今のフレームの画像）を Present し、ディスプレイがそれを表示する。垂直同期の設定によっては、ここで次の表示の時点まで待つ。

9.4Canvas を通らない経路

適合検査の GlyphConformance.CheckRendering（README §10）は、Canvas もカメラも使わずに同じシェーダで描く。CommandBuffer で一時の RenderTexture（ARGB32・linear）を透明にクリアし、正射影を置き、DrawMesh で字の Mesh を描いて、ReadPixels で読み戻す。_MainTex は MaterialPropertyBlock で渡し、クリップは Canvas と同じキーワードと _ClipRect を自分で入れる。シェーダが Canvas に依らず、描画パイプラインにも依らないことを、この経路が確かめる。

101 フレームの中の順序

§3〜§9 は 1 フレームの中で次の順に起きる。右肩は PlayerLoop の段の名前。

検証ビューは値が変わるたびに字の GameObject・Mesh を全部作り直す（README §10 の検証のための作り）。利用側のテキスト描画で毎フレーム文字列が変わるなら、GameObject を使い回し、GlyphGeometry を 1 つの Mesh へまとめて詰めるなど、§4〜§6 の作り方を変えればよい。§7 以降は変わらない。

12図の作り方

実データの図（図 2〜4・8・9 と表の数値）は、パッケージの Core/ と Bake/ のソースをそのままリンクした .NET 8 のコンソールプログラムで、インポーターと同じ FontBakeSpec.Parse → FontSpecBaker.BuildFace → SdfAtlasBaker.Bake を見本に対して走らせ、タイポグラフィテーブル・セル・ページの画素を書き出して描いた。ペンの位置・頂点・UV は T2FontText.Rebuild・SdfRepresentation.WriteGeometry・GlyphGeometry と同じ式で、フラグメントの値はシェーダ T2Font/SDF の frag と同じ式（bilinear・clamp で読んだ値・UV0.zw の微分から得た 1 表示 px・入れ子の面積の合成）を CPU で計算した。ブレンドの結果は Blend の式と sRGB の変換を同じく計算した値で、GPU が実際に書いた値ではない（GPU の補間の精度と sRGB の変換の丸めで 1 の差は出うる）。

図を作ったときの見本のアトラスの ComputeContentHash は 593ec06922b6d9a89ea658d2044a2526a8ce46017c4e2197cb2485b6f926a6fc（02 章の図と同じ）。ベイカーの出力が変われば値が変わるので、図が古くなったかの目安になる。
